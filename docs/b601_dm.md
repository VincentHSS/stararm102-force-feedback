# 方案二：B601-DM 独立 Python 遥操作

当前推荐入口是 [`integrations/b601/`](../integrations/b601/)。StarArm-102 Leader 直接通过 UART 读取，B601-DM 通过达妙串口桥或 SocketCAN 控制；**不加载 LeRobot、motorbridge 或 motorbridge-smart-servo**，没有手动 LD 扭矩控制台。

返回 [三种方案对照](../README.md)。自家 StarArm 从臂与 Lumos 的代码没有改动，Lumos 优化版仍只保存在本力反馈仓库内。

## 本次解决的两个问题

1. **持续零位误判**：新版本直接检查 StarArm 回包的帧头、长度、校验和、舵机 ID 和固件无效哨兵。只要本轮收到有效回包，角度持续为 0 也有效；不会因为数值和上次相同就判不可靠。保留丢包识别与按时间计算的突跳过滤，不通过屏蔽 `reliable` 标记来放行旧缓存。
2. **普通跟随延迟触发阻力/保持**：移除框架观察与动作处理链路，使用自己的控制循环。堵转比较上一帧已下发、已限速的目标；从臂还朝目标移动，或误差在收敛时，不按低跟随比例锁定。必须同时出现大角差、持续超出底载的负载和实际无进展，连续确认后才保持。

用户报告的 `motorbridge-smart-servo 0.0.4` 修复包在另一台 Linux 机器；本仓库没有取得或重新发布它。**本方案不依赖这个 SDK，所以不需要安装该 wheel。** 旧 LeRobot 方案仅作为 [历史存档](b601_lerobot_legacy.md) 保留。

## 安装

需要 Python 3.10+。达妙串口桥可在 Linux/Windows 使用；SocketCAN 使用 Linux 已配置的 CAN 接口。推荐新建单独 Python 环境，不需要安装 LeRobot、PyTorch、相机或模型依赖。

```bash
git clone https://github.com/VincentHSS/stararm102-force-feedback.git
cd stararm102-force-feedback/integrations/b601
python -m pip install -r requirements.txt
python teleop.py --help
```

已有仓库先更新代码。所有后续命令都在 `integrations/b601/` 下执行。

先运行无硬件模拟，确认环境正常；模拟不会打开任何串口/CAN，也不需要安装外部 Python 包：

```bash
python teleop.py --simulate
python teleop.py --simulate --simulate-stall 0
```

第一条应正常跟随，第二条模拟 Leader ID 0 对应关节堵住并触发保持。模拟不是实际机械臂性能测试。

## 从旧 LeRobot 版本切换

先停止原遥操作程序，避免两份程序占用同一个串口或 CAN。如果以前安装过本仓库钩子、需要恢复官方文件，在**旧环境**执行：

```bash
python -m stararm_auto_feedback.install --remove
```

这只是恢复旧环境的可选步骤，不是新 Python 程序的安装依赖。恢复器会检查备份与哈希；被手工改过的官方文件不会被直接覆盖。

新程序不会执行官方的自动零位重置、夹爪探零或断开回零。它采集当前配对姿态，并在执行前检查姿态误差；不写电机零位或 Flash。不要直接把 LeRobot 的校准 JSON 当成本程序配置。

## 端口与官方默认映射

复制示例配置：

```bash
cp b601.example.json my_b601.json
```

Windows 用 `Copy-Item b601.example.json my_b601.json`。编辑 `my_b601.json`：

| 参数 | 默认值 | 用途 |
| --- | --- | --- |
| `leader_port` | `/dev/ttyUSB0` | StarArm Leader UART，固定 1 Mbps；Windows 填实际 COM 端口 |
| `adapter` | `damiao` | `damiao` 为达妙专用串口桥；`socketcan` 为 Linux CAN 接口 |
| `follower_port` | `/dev/ttyACM0` | 达妙串口桥设备；SocketCAN 时填写 `can0` |
| `follower_baud` | `921600` | 达妙串口桥串口波特率 |
| `button_id` | `null` | 不读 HD 按钮；有按钮板时填实际 ID，如 7 |
| `calibration_verified` | `false` | 核对配对姿态、方向与限位后改为 `true`，才允许执行 |

SocketCAN 时先通过系统工具配置 CAN 比特率；脚本只打开已有接口，不修改系统 CAN 设置。程序当前不支持 RobStride 专用桥、MCU 自定义协议或达妙设备专有 USB API。

示例取自 Seeed 官方 B601-DM 默认配置，实际改过 ID、传动比例或方向的设备必须修改相应行：

| 关节 | Leader ID | 电机 CAN ID / 反馈 ID | 方向/比例 | 从臂软限位（度） | 模式 |
| --- | --- | --- | --- | --- | --- |
| shoulder_pan | 0 | 0x01 / 0x11 | -1 | -145 .. 145 | POS_VEL = 2 |
| shoulder_lift | 1 | 0x02 / 0x12 | -1 | -170 .. 0 | POS_VEL = 2 |
| elbow_flex | 2 | 0x03 / 0x13 | 1 | -200 .. 0 | POS_VEL = 2 |
| wrist_flex | 3 | 0x04 / 0x14 | 1 | -80 .. 90 | POS_VEL = 2 |
| wrist_yaw | 4 | 0x05 / 0x15 | 1 | -90 .. 90 | POS_VEL = 2 |
| wrist_roll | 5 | 0x06 / 0x16 | -1 | -130 .. 130 | POS_VEL = 2 |
| gripper | 6 | 0x07 / 0x17 | -6 | -270 .. 0 | FORCE_POS = 4 |

启动会只读检查模式以及实际 P/V/T 编码量程。模式不匹配时明确报错，不静默改写参数。先用厂商工具或已配置好的原控制环境设置模式，退出原程序后再使用本程序。

## 配对姿态、预览与执行

1. 停止其他控制程序，让两臂处于稳定、相互对应的参考姿态。执行启动要求 B601 电机处于未使能状态；退出时会断使能，需要支撑好机械臂。
2. 读取当前姿态，保存新的配置文件：

```bash
python teleop.py --config my_b601.json --capture paired.json
```

采集只读取回包和寄存器，不使能、不下发运动、不改零位；不会自动把 `calibration_verified` 改成 true。已有同名输出文件时拒绝覆盖，请换一个文件名。

3. 预览滤波与映射，并可记录诊断：

```bash
python teleop.py --config paired.json --diagnostics-file preview.csv
```

预览只读设备，既不控制从臂，也不改变 Leader 模式。核对配置中的方向、比例、限位和采集姿态后，将 `paired.json` 的 `calibration_verified` 改为 `true`。

4. 执行：

```bash
python teleop.py --config paired.json --execute --diagnostics-file run.csv
```

启动检查两臂与配对姿态的差异，再将从臂保持在当前姿态并采集约 1 秒底载。此时不要接触/阻挡从臂，之后进入自动跟随。`Ctrl+C` 退出会尝试逐个断使能 B601、释放 Leader，最后关闭设备；不会额外执行回零运动。

正常运行不输入扭矩或阻尼命令。HD 按钮启用时，按下保持 Leader 六个关节并冻结对应从臂目标，夹爪仍可跟随；松开按钮不能覆盖仍有效的自动堵转保持。

## 滤波、限速和抗误锁逻辑

- 自适应低通：低速抑制噪声，高速提高截止频率；输入死区避免静止微抖。
- 目标按实际时间限速，同时限制加速度、每帧步长及软限位。通信停顿后不发送大幅追赶目标。
- 启动时采样底载；跟随误差小时缓慢更新底载，堵转或手动保持时停止更新。对超出底载和死区的剩余负载平滑后映射阻尼。
- 堵转使用**已下发目标**与**本轮新位置反馈**，而不是滤波前 Leader 输入。仅仅大角差、正常慢速跟随或一次力矩尖峰都不满足堵转条件。
- 默认观察窗口 0.5 秒，连续两个异常窗口才确认；从臂朝目标有实际进展或角差收敛时清除异常计数。
- 自动保持时冻结全部从臂目标；触发关节误差连续恢复后重新进入阻尼。保持模式定期重发，防止后续阻尼覆盖。
- 单轮缺包先跳过运动、打断确认计时，不立即大力锁住。连续反馈超时或电机状态/温度/位置异常会锁存故障、请求 Leader 保持并停止新目标，检查后重启；不会在好坏读数间反复自动释放。

底载算法不是 URDF 重力补偿，也不能严格区分任意姿态下的重力、摩擦与外力。小误差时缓慢自适应也可能逐渐减弱持续接触反馈。不要把初始默认参数当成已完成的实机标定。

## 主要参数

修改 JSON 后重启生效。每关节方向、限位、速度与力矩标尺位于 `joints` 中。

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `loop_hz` | 100 | 期望循环频率，实际频率取决于 USB/UART/CAN 往返时间 |
| `read_timeout_s` / `link_timeout_s` | 0.015 / 0.25 秒 | 单设备查询等待与连续反馈丢失阈值 |
| `filter_cutoff_hz` / `filter_beta` | 5 / 0.15 | 自适应滤波最低截止频率与速度增益 |
| `input_deadband_deg` | 0.1 | 输入静止死区 |
| `input_max_speed_deg_s` / `input_jump_margin_deg` | 800 / 10 | Leader 突跳检查速度与容差，不是下发运动速度 |
| `speed_deg_s` | 关节 50、夹爪 100 | 从臂每关节速度限制，单位度/秒 |
| `motor_speed_deg_s` | 关节 100、夹爪 150 | DM 位置模式的追赶上限，与参考轨迹速度分开；旧配置不填时沿用 `speed_deg_s` |
| `max_step_deg` / `acceleration_deg_s2` | 2 / 300 | 单帧目标步长上限与加速度限制 |
| `baseline_s` / `baseline_adapt_s` | 1 / 5 秒 | 启动底载采集时长与正常跟随时的自适应时间常数 |
| `torque_filter_s` | 0.1 秒 | 负载平滑时间常数 |
| `torque_reference_nm` | 前三轴 5，其他 1 | 超额负载的归一化参考，不是电机额定值 |
| `torque_deadband_nm` | 前三轴 0.2，其他 0.1 | 扣除底载后的力矩死区 |
| `power_min_mw` / `power_max_mw` | 1 / 1000 | Leader 阻尼范围；SDK 协议单位 mW，不等于 Nm |
| `lock_deg` / `release_deg` | 20 / 8 | Leader 等效角差阈值 |
| `window_s` / `confirm_windows` | 0.5 秒 / 2 | 堵转观察窗口与连续确认次数 |
| `minimum_load_ratio` | 0.35 | 堵转需要的最低剩余负载比例 |
| `stalled_motion_deg` / `convergence_deg` | 0.5 / 1 | 一个窗口中判定有进展的位移/角差收敛量 |
| `release_stable_s` | 0.4 秒 | 自动释放的连续稳定时间 |
| `hold_mw` / `relock_s` | 6000 / 1 秒 | Leader 保持功率与重发间隔 |
| `gripper_force_ratio` | 0.1 | DM 夹爪力位模式电流/力矩限制比例，非运行时手动扭矩输入 |

## Windows 计时与响应调试

Windows Python 3.12 环境中，`time.monotonic()` 本机实际使用 GetTickCount64，精度为 15.625 ms；原版本日志因此出现 dt=0/16/31 ms。控制循环和串口查询现统一使用 `time.perf_counter()`（QPC），本机只读典型间隔约 10.3 ms，实际执行约 90–95 Hz。此频率取决于设备与环境，不代表固定保证。

原版本将参考轨迹和电机速度都限制为 50°/秒，参考更新较快时没有足够追赶余量。现在两者独立：普通示例目标仍为 50°/秒，电机追赶上限 100°/秒；夹爪分别为 100 / 150°/秒。量程检查和突跳过滤也采用实际电机速度上限。仅增加电机速度并不能消除内部位置响应的全部延迟。

软件参考轨迹现在根据剩余距离制动，到点后不越过目标；目标反转时取消旧方向的虚拟速度，避免参考轨迹继续往相反方向走。反转/停止时的参考速度会复位，软件加速度参数用于起步与同向变化，不是机械加速度的绝对保证。

曾在现场尝试根据从臂位置误差追加目标的补偿，但出现主臂静止时腕部自行摆动，现已彻底移除该试验代码及配置。当前运动目标只来自主臂输入，不能用原试验参数启用补偿；不改写电机 PID、模式、保护值或 Flash。

启动允许零位附近的小漂移，但仍检查原始配对误差，实际目标始终限制在软限位内。真实动态跟随滞后仍需逐轴确认，不能把循环频率提高等同于跟随性能已经解决。

## 诊断与真实边界

终端每约 2 秒显示实际 `loop`、`sent`、参考轨迹与实际位置的最大等效角差和状态。CSV 记录查询耗时、间隔、有效性、下发目标 `target`、实际位置 `actual`、力矩、底载与负载比例，并增加原始输入 `leader`、滤波输入 `filtered`、原始映射目标 `desired` 和限速参考轨迹 `reference`，区分输入滤波、软件限速与从臂响应的延迟。

100 Hz 是计划值；去掉框架也不能排除 USB、CAN 或电机配置导致的延迟。用 CSV 区分低更新率、目标限速和从臂实际跟不上。

每轮查询前丢弃已收到的旧数据，使用新接收回包更新本地序号和时间；相同位置的连续新回包仍有效。协议没有请求序号，不能严格区分极迟到的上一轮回复。达妙串口封装没有额外应用层校验；程序校验帧格式、ID、状态、限位与变化量，CAN 链路错误仍取决于适配器和硬件。

Leader `0x11` 保持指令不是从臂急停，也不等于硬件已锁住；重发仍依赖主循环、供电与通信。软件尚未完成实机保护性能验证。
